# Count failed stderr writes as unpersisted bytes

Slug: fix-k-exec-round-files-bounded
Model: not applicable — per-write byte accounting of two counters (kept, lost) inside one writer; no states or interacting rules
Acceptance:
- .kogen/intents/fix-k-exec-round-files-bounded/acceptance.feature
- features/steps/fix-k-exec-round-files-bounded__steps.js

This fixes an automated review finding on the landed k-exec-round-files-bounded change, about `stderrPersistence.Write` in `executor/claudecode/persistence.go`. The finding: "If `errf.Write` errors, the write returns the error and `copyRedacted` may stop reading. A chatty child then blocks on a full stderr pipe, which is the hang this change was meant to prevent. Short writes also leave `lost` undercounted."

The two parts of the finding were checked separately on current main (06064d5):
- **The hang does not reproduce.** `copyRedacted` (`executor/claudecode/redact.go`) already keeps draining after a write error with `io.Copy(io.Discard, r)`, and the existing `TestRedactCopyDrainsAfterWriteError` covers that. In a scratch probe, a child wrote 1048576 stderr bytes into a `round-1.stderr` symlinked to `/dev/full`. The round returned in 17 ms.
- **The undercount reproduces.** In that same probe, the terminal `executor_round_failed` event had `kept_bytes: 0` and no `stderr_persist_truncated` or `stderr_persist_unpersisted_bytes` at all. In a second probe the artifact took only its first 4096 bytes (the driver's `RLIMIT_FSIZE` set to 4096). That event had `kept_bytes: 4096` and also no unpersisted count.

The reason is that today, when the underlying write fails or is short, `Write` returns `(written, err)` or `(written, io.ErrShortWrite)`. That return skips `p.lost += …`. So neither the unwritten part of the within-cap slice nor any over-cap part is counted. Every later write after the failure also returns early.

**New `stderrPersistence.Write(b)` contract.** Let `n = min(len(b), cap-kept)` as today. When `n > 0`, it writes `b[:n]` to `w` once and adds the returned `written` count to `kept`. It then adds `len(b) - written` to `lost`. That is the unwritten remainder of `b[:n]` plus the over-cap bytes. When `n <= 0`, `written` is 0. It always returns `(len(b), nil)`. Any error or short count from `w` is swallowed, and the writer keeps accepting and counting later writes. After every call, `kept + lost` equals the total bytes passed to `Write`.

So stderr is always drained to its end. The round's `stderr_persist_unpersisted_bytes` counts every stderr byte that did not reach `round-N.stderr`, whatever the cause: the cap, a failed write or a short write. `stderr_persist_truncated: true` accompanies it, through the unchanged `addPersistence`.

**What still detects the failure.** The `retainedWriter` around the stderr file records the failure (`err`, `kept`). So the round still fails afterwards with `executor/failed: cannot persist round-N.stderr after K bytes`. Its `executor_round_failed` event still carries `artifact: "round-N.stderr"` and `kept_bytes: K`, as today. Because the stderr copy no longer sees a write error, a stderr write failure no longer ends the round early through `stderrFailed` ("artifact write failed"). The child's round runs to its end, and then the same artifact failure replaces the result. This follows directly from the requested swallowing.

**Unchanged.** The stderr redactor and `copyRedacted`, `retainedWriter`, stream (`round-N.jsonl`) persistence, the cap, and the marker text and its placement all stay as they are. The marker is still written through the stderr `retainedWriter`, so it is not persisted once that file has failed. Session wiring is also unchanged. No unrelated changes.

**Documentation.** Update the stderr part of "Claude Code round artifact persistence" in `docs/executor-contract.md`, and the `Options.StderrPersistBytes` comment in `executor/claudecode/claudecode.go`. They must say that `stderr_persist_truncated` / `stderr_persist_unpersisted_bytes` also count stderr bytes that a failed or short write to `round-N.stderr` did not persist, and that stderr keeps draining after such a failure. "Under the cap these fields and markers are absent" becomes: under the cap and without a failed write.

## Decisions
- Reproduce first. The hang half of the finding does not reproduce on main: `copyRedacted` already drains after write errors. The undercount half does reproduce, through the real adapter, both for an artifact that refuses every write and for one that takes only a prefix. The fix proceeds for the part that holds. (source: request)
- Swallow write errors in `stderrPersistence.Write` after counting the bytes as lost, keep draining, and count the unwritten remainder of a short or failed write as lost. (source: request)
- The round still fails with the existing persisted-artifact error, because `retainedWriter` keeps recording the failure. Only the early "artifact write failed" stop for stderr goes away, as a consequence of swallowing. (source: request)
- Keep every existing test green. The one existing assertion that the swallowing makes obsolete is updated as listed under Tests. Make no unrelated changes. (source: request)

## Tests
- A failed or short underlying write is reported to the caller as a full write, its unwritten bytes and any over-cap bytes are counted in `lost`, and later writes keep being accepted and counted: add a new regression test `TestStderrPersistenceCountsUnwrittenBytes` in `executor/claudecode/persistence_test.go`, reusing `partialSink`. (1) Use cap 100 and `partialSink{limit: 3}`, which errors. Writing `"abcdef"` returns `(6, nil)` with `kept == 3`, `lost == 3`. Then writing `"gh"` returns `(2, nil)` with `kept == 3`, `lost == 5`. (2) The same with `short: true`, a short write without an error, gives the same results. (3) Use cap 4 and `partialSink{limit: 2}`. Writing `"abcdef"` returns `(6, nil)` with `kept == 2`, `lost == 4`. The test must fail on current main (regression)
- A round whose stderr artifact refuses every write drains a chatty child, still fails with the artifact error, and reports every stderr byte as unpersisted: add a new integration test in `executor/claudecode/persistence_test.go`. It uses the existing harness, links `round-1.stderr` to `/dev/full` (skip where it cannot be opened, as `TestFinalPersistenceFailures` does), and uses a wrapper that writes 1048576 bytes to stderr before exec'ing the fake. It asserts the error detail `cannot persist round-1.stderr after 0 bytes`. It also asserts that the single `executor_round_failed` event has `artifact: "round-1.stderr"`, `kept_bytes: 0`, `stderr_persist_truncated: true` and `stderr_persist_unpersisted_bytes: 1048576`. Also add acceptance scenario 1 through the public adapter (regression)
- A round whose stderr artifact accepts only a prefix counts the unwritten remainder: acceptance scenario 2 (`RLIMIT_FSIZE` 4096, 1048576 stderr bytes → `round-1.stderr` holds 4096 bytes, `kept_bytes: 4096`, `stderr_persist_unpersisted_bytes: 1044480`) (regression)
- The redactor flush through `stderrPersistence` no longer returns the file's error, but the failure is still recorded for the round: update `TestRetainedWritesAndRedactorFlush`. Its second half now expects `redactor.Flush()` to return nil, `file.err != nil`, `file.kept == 2`, the sink to hold `"ab"`, and `capped.lost == 2` (existing)
- Stderr keeps draining after a write error, under-cap rounds without write failures report no stderr persistence fields, and artifact failures keep their `artifact`/`kept_bytes` event and error: these stay covered, unchanged, by `TestRedactCopyDrainsAfterWriteError`, `TestFinalPersistenceFailures`, `TestSuccessfulStderrEvidenceBytes` and the landed k-exec-round-files-bounded and k-exec-round-stream-write-failure acceptance (existing)
- The documentation now says failed and short stderr writes are counted: no executable test; check the changed text of `docs/executor-contract.md` and the `Options.StderrPersistBytes` comment (existing)

## Feasibility
- Reproduced the undercount on current main through the public adapter. A scratch driver, the same Go source as the step file's driver, was built from the repository root with `go build -o <tmp>/driver <tmp>/main.go` (go1.27.2 linux/amd64). With `{"Stderr":1048576,"Sink":"full"}` it reported `executor/failed: cannot persist round-1.stderr after 0 bytes` in 17 ms, with `kept_bytes: 0` and no `stderr_persist_*` fields. With `{"Stderr":1048576,"Sink":"fsize","Limit":4096}` it reported `… after 4096 bytes` in 16 ms, with `kept_bytes: 4096`, a 4096-byte `round-1.stderr` and no `stderr_persist_*` fields. The probes confirm that `/dev/full` exists here and that a lowered `RLIMIT_FSIZE` yields a real partial write (Go ignores SIGXFSZ), so this is not a hang. They do not prove the post-fix counts, which follow from the `Write` contract (`lost = total − written`).
