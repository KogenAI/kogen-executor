# Run setup-token sign-in on the managed runtime

Slug: e-claude-setup-token-managed-runtime
Model: not applicable — one call that installs (with the existing installer) and runs one child process; it keeps no state of its own
Acceptance:
- .kogen/intents/e-claude-setup-token-managed-runtime/acceptance.feature
- features/steps/e-claude-setup-token-managed-runtime__steps.js

Studio decision kogen/claude-login-uses-kogens-own-claude-code-20261107 r1 (owner, 7 Nov 2026), first of two changes: this one in kogen-executor, then the kogen CLI uses it. Today a Claude subscriber has to install Claude Code themselves just to run `claude setup-token`, although Kogen installs its own pinned copy (Version, under ~/.kogen/claude-code/<Version>/claude) at the first role that needs it; nothing exported lets the CLI install that runtime and run its sign-in before any role exists.

Package `executor/claudecode` gains one exported function, `SetupToken(ctx context.Context, home string, out io.Writer) (string, error)`. It installs the pinned runtime when it is missing, with the same installer the first role uses (an installed runtime is used as it is and nothing is downloaded), runs that runtime's `setup-token` with its own browser sign-in, its configuration under `ConfigDir(home)`, its prompts and sign-in URL written to `out` and the terminal passed through, and returns the token the runtime printed, trimmed, and nothing else. An empty or unparsable result is an error. Errors name what failed (install, run, empty token) and the exact retry command `kogen provider login claude-code`. The token is never written to `out`, logs or error text. New, Probe, Start, the roles and every existing message stay as they are; nothing is removed. The existing test files of the package and of the contract suite stay byte for byte as they are, and go.mod and go.sum do not change.

## Decisions
- `SetupToken(ctx context.Context, home string, out io.Writer) (string, error)` is the only new exported identifier of package `executor/claudecode`; its helpers stay unexported (evidence: executor/claudecode/runtime.go; executor/claudecode/claudecode.go) (source: request)
- Installation is the roles' own: an adapter made by `New(Options{Home: home, Stderr: out})` runs its `ensureRuntime`, which creates Root and ConfigDir as today and installs only when `RuntimePath(home)` is absent; a present runtime is used as it is, without a version check and without any download; the installer's progress and lock-wait lines (`kogen: installing Claude Code <Version> into <dir>` and the others) go to `out` (evidence: executor/claudecode/runtime.go; executor/claudecode/claudecode.go) (source: request)
- The run executes `RuntimePath(home)` with exactly one argument, `setup-token`, and the adapter's child environment without a home override and without a token (`childEnv` of the inherited environment: the strip list, the set variables and `CLAUDE_CONFIG_DIR=ConfigDir(home)`; no token file descriptor) (evidence: executor/claudecode/args.go; executor/claudecode/claudecode.go) (source: request)
- The terminal passes through: the child's standard input is `os.Stdin` as it is at the call, and the child stays in the caller's process group (no `Setpgid`, unlike the existing no-terminal `run`), because a process in a background process group is stopped when it reads or configures the terminal (evidence: executor/claudecode/claudecode.go) (assumption: the sign-in needs the terminal for the pasted code, as the pinned runtime's `Paste code here if prompted >` prompt showed in this session; a Ctrl-C at the terminal then reaches both Kogen and the runtime) (source: request)
- The runtime's standard error is written to `out` as it arrives; its standard output is captured whole and also written to `out` as it arrives, except that nothing from the first occurrence of the text `Your OAuth token` onward is written; bytes before that text reach `out` without waiting for a line end, holding back only a trailing part that could be the start of `Your OAuth token`; writes to `out` are serialized (assumption: in pipe mode the pinned runtime prints its paste prompt without a line end and the token after a `Your OAuth token (valid for …):` line, as observed and as its strings show) (source: request)
- The token is parsed from the whole captured standard output after the child exits: escape sequences (CSI `ESC [ … final byte` and OSC `ESC ] … BEL or ESC \`) and carriage returns are removed; after the first line containing `Your OAuth token`, blank lines are skipped and the following non-blank lines are trimmed and joined, up to a blank line, a line starting with `Store this token securely` or the end; the result is the token only when it is non-empty and consists of ASCII letters, digits, `-` and `_`; otherwise there is no token (assumption: a long token may be wrapped over several indented lines, as the sign-in URL was wrapped in pipe mode in this session) (source: request)
- A non-zero exit or other run failure wins over a printed token: no token is returned then (source: request)
- Every SetupToken error is `executor.Fail(executor.ReasonUnavailable, …)`, so its text is `executor/unavailable: <detail>`, with exactly these details: install failure `cannot install Kogen's Claude Code: <the installer's detail>; run `kogen provider login claude-code` to retry`; run failure `Kogen's Claude Code `setup-token` failed: <the process error, such as exit status 3>; run `kogen provider login claude-code` to retry`; empty or unparsable token `Kogen's Claude Code `setup-token` printed no token; run `kogen provider login claude-code` to retry`; no detail carries the runtime's standard output (evidence: executor/claudecode/runtime.go; executor/claudecode/claudecode.go) (source: request)
- The contract suite is not changed here: it pins what consumers already use, and the kogen CLI starts using SetupToken in the second change, which pairs its contract case with its consumer test (evidence: contract/doc_test.go; contract/claudecode_runtime_test.go; README.md) (assumption: the owner accepts adding the contract case with the kogen CLI change rather than now) (source: request)
- "Unchanged" is checked against this checkout's HEAD: go.mod, go.sum and every test file tracked under `executor/claudecode` and `contract` keep their SHA-256 digests, and those two packages' tests pass as the configured go-test check runs them (`GOFLAGS=-trimpath go test -count=1`); the Build may add new test files (evidence: .kogen/project.yaml; go.mod; go.sum; contract/doc_test.go) (source: request)
- Acceptance drives SetupToken through a capture test overlaid on the package with `go test -overlay`, a fake runtime script served by a local origin through SeamEnv or placed at RuntimePath(home), and a file as standard input; while package claudecode exports no SetupToken, the step overlays a stub so the capture still runs and the property steps show the missing behaviour (evidence: features/steps/k-exec-install-local-write-failure-named__driver.js; executor/claudecode/runtime.go; executor/claudecode/fake_test.go) (assumption: acceptance runs on a platform the runtime supports, macOS on Apple Silicon or Linux x86-64, with `go`, `sh` and `ps` available) (source: request)

## Tests
- A missing runtime is installed once with the roles' installer and its `setup-token` runs with Kogen's configuration directory, the caller's standard input and process group: integration test in executor/claudecode with a fake runtime served through SeamEnv (integration)
- An installed runtime is used as it is and nothing is downloaded: integration test in executor/claudecode with a fake runtime at RuntimePath(home) and a counting local origin (integration)
- The runtime's prompts, URL and standard error reach out as they arrive, nothing from `Your OAuth token` onward does, also when that text is split across writes: integration test in executor/claudecode with a fake runtime (integration)
- The token is parsed after the marker line, joined across wrapped lines and without escape sequences; a missing or unparsable token is the empty-token error: integration test through SetupToken with fake runtimes (integration)
- Install, run and empty-token failures are executor unavailable errors naming the failure and the retry command, never the token, and a non-zero exit returns no token: integration test through SetupToken with fake runtimes and a failing local origin (integration)
- New, Probe, Start and the roles behave as before, their tests unchanged, and no dependency is added: acceptance scenario checking the digests of go.mod, go.sum and the existing test files and running the existing package and contract tests (scenario)
