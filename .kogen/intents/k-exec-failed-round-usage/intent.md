# Report usage on failed Claude Code rounds

Slug: k-exec-failed-round-usage
Model: not applicable — the change adds fields observed from a round's own result line to one emitted event; it adds no state, transition or retry rule, and the session's cost baseline is left exactly as today
Acceptance:
- .kogen/intents/k-exec-failed-round-usage/acceptance.feature
- features/steps/failed_round_usage.js
- features/steps/failed_round_usage_capture_test.go.txt

Today a Claude Code round whose result line is an error result (any `subtype` other than `success`/`error_max_turns`, an `is_error` result, a usage-limit or an auth result) returns from `roundRun.finish` (executor/claudecode/stream.go, the `default:` branch and the earlier auth check) before `s.mapUsage(res, r.model)` runs, so its `executor_round_failed` event (built in `session.Round`, executor/claudecode/session.go) carries only `event`, `role`, `round`, `reason`, `detail` (bounded to 400 bytes), `deadline_remaining_ms` and the optional interrupt and rate-limit keys. Tokens, turns and cost of the failed round are lost, so a rescued or retried workflow under-reports what it spent and a failed round cannot be priced.

After this change, an `executor_round_failed` event of a round whose stream reached a result line also carries what that result line reported: `usage` (exactly the object shape of `executor_round_ended`'s `usage`), `num_turns`, `subtype` and `terminal_reason`. Fields the result did not report stay absent, never zero. Nothing else changes: every failure reason and detail text, the 400-byte detail bound, the classification of usage-limit, auth, context-budget and protocol failures, the refusal of rounds after a failed round, the interrupt and rate-limit keys, and the `executor_round_ended` event (byte for byte) stay exactly as they are. Nothing is replaced or removed.

Production changes belong in executor/claudecode/stream.go and executor/claudecode/session.go; focused tests go in executor/claudecode. Do not edit prompts, agent/, runtime.go, or the existing contract/ cases (no consumer reads the new keys yet).

## Decisions
- `executor_round_failed` carries, when the result line reported them, the round's usage in the same shape as `executor_round_ended`, `num_turns`, and the result `subtype`/`terminal_reason`; absent fields stay absent, never zero. (source: request)
- Cost accounting (`prevCost`) and every failure reason, bound and retry rule stay exactly as they are; `executor_round_ended` for a success result is unchanged byte for byte. (source: request)

Technical rules settled by shaping (they fill in the request's unspecified details; they are not new settings). Which failed events get the keys: every `executor_round_failed` emitted for a round whose stream reached a `type: "result"` line (`roundRun.result != nil`), whatever failure reason follows from it (error result, usage limit, auth refusal, context budget, nonzero exit after a success result, protocol checks of the result, or a cancellation after the result). A round that ended before any result line (no init, no result, a broken line, a cancellation before the result) gets none of the four keys.

The `usage` key is present when the result line has a JSON object `usage` or a numeric `total_cost_usd`; otherwise it is absent. Its value is built by exactly the existing `mapUsage` rules and `usageEvent` shape: `state` (`complete`/`partial`/`unknown`), `source` `harness`, `input` = input_tokens + cache_read_input_tokens + cache_creation_input_tokens only when all three are reported, `cached` = cache_read_input_tokens, `output` = output_tokens, `reasoning` null, `model` = the init event's model; an unreported token field is `null` inside the object, never 0. `cost_usd` is the delta of the cumulative `total_cost_usd` since the previous round of the session (rounded to 1e-9), `null` when absent or below the previous total — the same rule as `executor_round_ended`. A failed round does not advance `prevCost`.

`num_turns` is present only when the result's `num_turns` is a nonnegative integer count (the existing `countPtr` rule), with that value. `subtype` and `terminal_reason` are present only when the result carries them as nonempty strings, copied unchanged. These keys sit at the top level of the event, beside `reason` and `detail`, exactly as `num_turns` and `terminal_reason` do on `executor_round_ended`.

## Tests
- An error result with usage, `num_turns`, `subtype` and `terminal_reason` puts them on `executor_round_failed` with the unchanged reason and detail: acceptance through the real adapter `Round` on the contract fake `claude`, and a focused test in executor/claudecode (integration)
- An error result without usage fields gives no `usage` key, and a result without `num_turns`/`terminal_reason` gives no such keys; partially reported usage keeps unreported token fields null, not 0: acceptance scenarios plus the focused test (integration)
- A usage-limit result and an auth result (stored token, assistant `authentication_failed` or 401 text) keep reasons `usage_limit` and `auth_refused` and carry the result's usage: acceptance for usage-limit, add a focused executor/claudecode test for the auth result using the existing token fake (regression)
- A failed later round's `cost_usd` is the delta of `total_cost_usd` since the previous round, the same rule as `executor_round_ended`: two-round acceptance scenario (integration)
- A round that ends before any result line gets none of the new keys and keeps reason `protocol`: acceptance scenario (integration)
- `executor_round_ended` for a success result is unchanged byte for byte, and all other failure classification, bounds and the no-continuation-after-failure rule are unchanged: exact-line acceptance scenario plus the existing executor/claudecode and contract/ suites unchanged (existing)
