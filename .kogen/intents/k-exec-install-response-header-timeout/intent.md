# Bound the wait for runtime download headers

Slug: k-exec-install-response-header-timeout
Model: not applicable — the change adds one per-request time bound and its failure classification to the existing binary retry loop and the single manifest request; it introduces no new state or interacting rules
Acceptance:
- .kogen/intents/k-exec-install-response-header-timeout/acceptance.feature
- features/steps/k-exec-install-response-header-timeout__steps.js
- features/steps/k-exec-install-response-header-timeout__driver.js

The pinned runtime download in executor/claudecode/runtime.go bounds only the gap between body bytes: the idle timer (downloadIdleTimeout) starts after the HTTP response headers have arrived. Today, if a server or middlebox accepts the connection and never sends a response status, or sends the status line and never finishes the headers, the request waits until the caller's context ends. The manifest request (`fetchManifest`/`get`) behaves the same way. A caller without a deadline therefore waits forever while it holds the exclusive install lock (`<home>/.kogen/claude-code/install.lock`), and every other Kogen process that needs the runtime waits silently behind it.

After this change, each request waits for its response headers only for a bounded time. That applies to every binary download attempt and to the manifest request. When the bound expires, the attempt fails as a transient transport failure. Binary attempts are then retried under the existing bounded retry policy: 3 attempts in total, pausing 1× and then 2× the retry delay in between. After the last attempt, the unavailable message names the source and says the server did not answer. As on every failed install, the `.partial-*` directory is removed and the install lock is released. The bound ends when the complete response headers arrive. After that, only the existing body idle bound applies, so a server that answers promptly but streams slowly is never cut by the header bound. Failures that carry an HTTP status keep their current classification. A body stall stays a non-retried "connection stalled" failure, and cancellation or a deadline from the caller keeps its existing classification. This change adds no user setting, no environment variable, no flag, no total transfer deadline and no new dependency. It also does not change the pins, checksum, size or version verification, or atomic publication.

## Decisions
- Name the production bound `const downloadHeaderTimeout = 30 * time.Second` in executor/claudecode/runtime.go, next to `downloadIdleTimeout`. The request asks for a named constant that is not a user setting; the name and the 30-second value are technical choices settled here, matching the idle bound. (source: request)
- Add the test seam `func (a *adapter) setDownloadHeaderTimeoutForTest(d time.Duration)`. It sets a per-adapter duration, and a zero value means `downloadHeaderTimeout`. This follows the existing `setDownloadIdleTimeoutForTest` and `setDownloadRetryDelayForTest` convention. Do not read any environment variable, CLI flag or configuration for this bound. (source: request)
- The bound applies anew to each binary attempt and to the manifest request. It runs from no later than the moment the request has been written until the complete response headers (status line and header block) have been received. A status line alone, or a partial header block, does not end it. Once the headers are complete, the bound stops and never applies to body reads; body gaps are governed only by the existing idle bound. One acceptable implementation is a per-adapter `http.Client` whose `http.Transport` (cloned from `http.DefaultTransport`) sets `ResponseHeaderTimeout`. Another is a timer that cancels the request's derived context until `Do` returns. Either way, the expiry must be told apart from caller cancellation. (source: request)
- When a binary attempt's bound expires, the attempt fails with the cause text `the server did not answer` and is retryable, like any other transport failure. Each attempt that will be retried prints one line to the adapter's stderr in the existing format `kogen: download attempt <n> failed: executor/unavailable: cannot download Claude Code 2.1.312 from <source>: the server did not answer; retry after pause\n`. Exhaustion returns executor/unavailable with the detail `cannot download Claude Code 2.1.312 from <source>: the server did not answer; 3 attempts`. (source: request)
- The manifest keeps the existing policy: the retry loop covers only the binary, so the manifest is requested exactly once. When its bound expires, `ensureRuntime` returns executor/unavailable with the detail `cannot download Claude Code 2.1.312 from <origin>/2.1.312/manifest.json: the server did not answer`. No binary request is made, and the detail has no attempt count. (source: request)
- Cancellation or a deadline from the caller, at any point, still returns classify(ctx) (executor/interrupted or executor/deadline), never `did not answer`. HTTP status failures are unchanged: 429 and 500–599 are retried, other statuses are not, and messages keep `HTTP <status>`. Body idle stalls keep `connection stalled` and are not retried. (source: request)
- Acceptance runs a supplied Go test through `go test -overlay`. That test uses these existing package internals, which must stay available with their current signatures: `New(Options{Home, Stderr})`, the adapter fields `goos` and `goarch`, `setDownloadIdleTimeoutForTest`, `setDownloadRetryDelayForTest`, `ensureRuntime`, `Root`, `RuntimePath`, `SeamEnv` and `Version`. Do not add a file named executor/claudecode/intent_header_timeout_capture_test.go, because the overlay supplies that path. (source: request)

## Source comparison
- Addressed: Problem (a silent server or a status line without finished headers holds the request and the lock until the caller's context ends, for the binary and the manifest). Acceptance rows `silent`, `partial-headers` and `manifest-silent` each reproduce it. On the unchanged tree, each of them waited until the 8-second caller deadline and returned executor/deadline.
- Addressed: Need, "bounded by a named constant, which is also a test seam and not a user setting". The named-default step checks `downloadHeaderTimeout = 30 * time.Second` in runtime.go, and every row calls `setDownloadHeaderTimeoutForTest` with 300 ms (5 s in the `deadline` row). Verification fails with a message naming the seam when it is absent.
- Addressed: Need, "retried under the existing bounded retry policy; after the last attempt the unavailable message names the source and says the server did not answer". Row `silent` expects 3 binary requests, 2 retry lines that each name their attempt number and `did not answer`, and a final executor/unavailable naming the binary URL with `did not answer` and `3 attempts`.
- Addressed: Need, "partial directory is removed and the install lock released". Every row requires 0 `.partial-*` entries and an install.lock that a non-blocking flock can take at once after `ensureRuntime` returns.
- Addressed: Need, "a server that answers promptly but streams slowly is never cut". Row `slow-body` sends the headers and the first quarter at once, then three gaps of 400 ms. Each gap is longer than the 300 ms header bound and shorter than the 2 s idle bound. The row expects one request, no retry, a successful install and at least 1000 ms elapsed.
- Addressed: Need, "Failures that carry an HTTP status keep their current classification". Rows `503` (3 attempts, retry lines without `did not answer`, final `HTTP 503` and `3 attempts`) and `404` (1 request, no retry, `HTTP 404`) run with the header bound active.
- Addressed: synthetic acceptance 1 is the `silent` row: each hung attempt is held open by the client for 200–1500 ms with the 300 ms bound, the final message names the source and says it did not answer, no partial directory remains and the lock is immediately free. Synthetic acceptance 2 is the `silent-once` row: the first attempt gets no answer, the second gets the file, the install succeeds, and exactly 1 retry line appears on stderr. Synthetic acceptance 3 is the `slow-body` row. Synthetic acceptance 4 is the `manifest-silent` row: a bounded failure naming the manifest URL, exactly 1 manifest request and 0 binary requests.
- Added for precedence (existing behavior that is kept): row `deadline` has a 400 ms caller deadline while the header bound is 5 s, and it stays executor/deadline without `did not answer`.
- Settled technical literals, not product additions: the constant name, its 30 s value, the seam name, the cause text `the server did not answer`, and the single manifest attempt, which follows the existing binary-only retry policy. Nothing in the request is omitted, conflicting or superseded. README, .kogen/project.yaml and the protection contract are unchanged. No required implementation edit touches a protected path.

## Tests
- A binary origin that never answers is bounded, retried 3 times and then reported as unavailable, naming the source and `did not answer`, with cleanup and the lock released: acceptance row `silent`, plus a focused runtime_test.go regression test with a short header seam (regression)
- A status line without completed headers is bounded the same way: acceptance row `partial-headers` (regression)
- A silent first attempt followed by a served file installs on the second attempt with exactly one retry line on stderr: acceptance row `silent-once` (integration)
- Prompt headers followed by a slow body, with gaps longer than the header bound and shorter than the idle bound, install normally: acceptance row `slow-body` (integration)
- A silent manifest origin gives a bounded single-attempt unavailable failure naming the manifest URL, with no binary request: acceptance row `manifest-silent`, plus a focused runtime_test.go test (regression)
- HTTP status failures keep their retry classification and messages while the header bound is active: acceptance rows `503` and `404`, plus the existing TestDownloadRetryTimingAndFreshBody and TestInstallRefusals (existing)
- Caller deadline precedence over the header bound: acceptance row `deadline`, plus the existing TestDownloadContextStopsWithoutRetry (existing)
- The named 30 s production default and its per-adapter seam: acceptance named-default step and seam verification in every row (unit)
- Body idle stalls, lock serialization, pins, verification and publication stay unchanged: the existing runtime_test.go tests and the configured Go checks (existing)
