# Fix tool-argument secret leaks and false masking

Slug: tool-args-log-leaks-secrets-and-masks-commands
Model: not applicable — each record's arguments are a pure function of one tool_use input and the adapter's fixed environment; nothing carries across calls or rounds
Acceptance:
- .kogen/intents/tool-args-log-leaks-secrets-and-masks-commands/acceptance.feature
- features/steps/tool-args-log-leaks-secrets-and-masks-commands__steps.js

The Claude Code adapter (`executor/claudecode`) logs each tool call's `input` as the `arguments` of its `executor_tool` run-log record, after redaction (`executor/claudecode/arguments.go`: `secretNamed`, `secretEnvValues`, `redactSecrets`, `processValue`). Today that redaction leaks real credentials in common spellings and token shapes, and it masks harmless values. This change makes it one consistent rule set. The replacement stays the existing `[redacted]` mark, and the shape stays "NAME stays, VALUE goes". This Intent replaces the separate Intents k-arg-redact-quoting-and-keyvalue-forms, k-arg-redact-secret-name-forms, k-arg-redact-nonsecret-names and k-exec-token-pattern-coverage. Their already-delivered behavior is kept as stated below.

Unchanged: the stored-token rule, the private-key block rule, the URL-password rule, the `Authorization: <scheme> <credential>` rule, the existing token formats (`gh?_`, `github_pat_`, `sk-`, `AKIA`/`ASIA`, `xox?-`), the 8-byte minimum for environment values, the order "environment values first, then the text rules", the string bound (4096/256), the whole bound (65536), the event fields and where events go. The way each form finds its NAME is unchanged. Only the decision "is this NAME secret-named" changes (rules 1–3), plus the value forms and token shapes in rules 4–5. `secretNamed` also chooses which environment values are redacted. That choice already applies to round stderr and the permission-denial display (`stream.go`), so the new name rules apply there too. This is the same single rule set, not a new destination.

## Rules

1. Words of a NAME. Remove leading `-`. List A splits the NAME on `_`, `-` and `.` (today's spelling). List B also splits each piece at camelCase boundaries: before an uppercase letter that follows a lowercase letter or a digit, and before an uppercase letter that is followed by a lowercase letter and preceded by an uppercase letter. Drop empty words and compare words case-insensitively. Examples: `accessTokenFile` → A `ACCESSTOKENFILE`, B `ACCESS TOKEN FILE`; `_authToken` → B `AUTH TOKEN`; `X-Api-Key` → `X API KEY`; `db.password` → `DB PASSWORD`; `--PaSsWoRd-FiLe` → A `PASSWORD FILE`.
2. Secret-named. A NAME is secret-named when list A or list B contains a secret word or an adjacent secret pair, and rule 3 does not exempt it.
   - Secret words: `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `APIKEY`, `CREDENTIAL`, and their plurals `TOKENS`, `SECRETS`, `PASSWORDS`, `PASSWDS`, `PASSPHRASES`, `APIKEYS`, `CREDENTIALS`. Also `COOKIE`, `BEARER` and `AUTHORIZATION`. Also the run-together compounds `AUTHTOKEN`, `ACCESSTOKEN`, `REFRESHTOKEN`, `CLIENTSECRET` and `PRIVATEKEY`. A run-together word matches only when the whole word equals one of these: `tokenizer`, `keyboardLayout` and `mytoken` match nothing.
   - Secret pairs (two adjacent words): `API KEY`, `ACCESS KEY`, `PRIVATE KEY`, `ENCRYPTION KEY`, `SIGNING KEY`, `MASTER KEY`, `SESSION KEY`, `DECRYPTION KEY`.
   - `TOKENS` as a count: a NAME whose only secret word is `TOKENS` is secret-named only when its value is not a count. A count is a JSON number, or a value that is one or more ASCII digits once one pair of surrounding quotes is removed. So `--max-tokens=4096`, `TOKENS=4096` and the JSON key `"max_tokens": 4096` stay, and `API_TOKENS=s3cr3tVALUE9x` is redacted. For environment entries, the value is the entry's VALUE.
   - Still secret-named: `API_TOKEN`, `--password`, `DB_PASSWORD`, `client-secret`, `GITHUB_TOKEN`, `--api-key`.
3. Non-secret names. A NAME is not secret-named when the last word of list A or of list B is one of `FILE`, `PATH`, `STDIN`, `LIMIT`, `COUNT`, `LENGTH`, `SIZE`, `NAME`, `HELPER`, `TTL`, `MAX`, `MIN`, or when the first word of list A or of list B is `NO`. Examples: `TOKEN_COUNT`, `--token-limit`, `PASSWORD_FILE`, `--password-file`, `--password-stdin`, `--no-password`, `CREDENTIAL_HELPER`, `SECRET_NAME`, `cookieCount`, `accessTokenFile`, `--no-cookie`, `NO_PASSWORD`. A non-secret option never takes the following word as a value. `docker login --password-stdin registry.example.com` and `pg_dump --no-password db` are logged byte for byte. This exemption wins over rule 2, even in the rare names that today's spelling alone made secret-named.
4. Value forms. The existing forms keep working with the new name rule. Each replaces the whole value and keeps the NAME and the surrounding text:
   - Assignments `NAME=VALUE`, options `-NAME VALUE`/`--NAME VALUE`, and JSON object keys (the whole value of a secret-named key).
   - `"name": "value"` and `name: value` pairs in JSON or YAML, single- or double-quoted or unquoted, also inside a larger shell string. A quoted value keeps its quotes around `[redacted]`.
   - `-u`/`--user user:password`: the user and `:` stay.
   - `$'…'` and `\"…\"` values: replaced whole, including the closing quote, so no fragment or stray quote stays.
   - `-H`/`--header` quoted header arguments: the whole value up to the closing quote is replaced when the header name is `Cookie` or `Set-Cookie`, contains `KEY`, `TOKEN`, `SECRET` or `AUTH` case-insensitively (as today), or is secret-named by rules 1–3. Example: `curl -H "X-Password: open s3cr3tVALUE9x" h` → `curl -H "X-Password: [redacted]" h`.
   - New, Cookie headers anywhere: `Cookie:` or `Set-Cookie:` (case-insensitive) at the start of the string or after whitespace, a newline, `"` or `'`. After optional spaces or tabs, the whole value becomes `[redacted]`. The value runs to the next `"` when the name directly follows `"`, to the next `'` when it directly follows `'`, and otherwise to the end of the line or string. The closing quote stays. Example: `echo "Cookie: theme=dark; session=s3cr3tVALUE9x" > req.txt` → `echo "Cookie: [redacted]" > req.txt`.
5. Token shapes. Add these to the existing token formats. Each starts at a word boundary and is replaced whole, wherever it occurs (in a URL, a quoted string or a JSON string value), regardless of any NAME:
   - `sk_live_`, `rk_live_` or `sk_test_` followed by at least 24 letters or digits;
   - `glpat-` followed by at least 20 letters, digits, `_` or `-`;
   - `npm_` followed by at least 36 letters or digits;
   - `AIza` followed by at least 35 letters, digits, `_` or `-`;
   - `xapp-` followed by letters, digits and `-` (at least one);
   - a JWT: `eyJ` followed by at least one base64url character (letters, digits, `_`, `-`), then `.`, at least one base64url character, `.`, and at least one base64url character.
   Not replaced: `npm_config_cache`, `sk_learn`, `eyJ` alone, `glpat-` alone, `AIza` followed by fewer than 35 characters, `sk_live_` + 23, `glpat-` + 19, `npm_` + 35.
6. Precedence. Stored-token, environment-value and token-shape redaction still apply to every string regardless of NAME exemptions. A secret-named environment value of at least 8 bytes (now including names such as `AWS_CREDENTIALS`) is replaced wherever it appears. Everything redacted today stays redacted, except names that rule 3 now exempts in a camelCase spelling.

## Decisions
- One consistent rule set with the same `[redacted]` mark and "NAME stays, VALUE goes" (source: request)
- Value forms: secret-named JSON/YAML pairs (also inside shell strings), secret-named HTTP headers, the whole Cookie/Set-Cookie value, the `-u`/`--user` password with the user kept, and whole `$'…'`/`\"…\"` values with no fragment or quote left (source: request)
- Name spellings: split on `_`, `-`, `.` and camelCase; secret words are the existing list, plurals of its single words, `COOKIE`, `BEARER`, `AUTHORIZATION`, and the pairs `ENCRYPTION_KEY`, `SIGNING_KEY`, `MASTER_KEY`, `SESSION_KEY`, `DECRYPTION_KEY`; a run-together lower-case name matches only as an exact known compound (`APIKEY`, `AUTHTOKEN`, `ACCESSTOKEN`, `REFRESHTOKEN`, `CLIENTSECRET`, `PRIVATEKEY`) (source: request)
- Non-secret names: last word `FILE`, `PATH`, `STDIN`, `LIMIT`, `COUNT`, `LENGTH`, `SIZE`, `NAME`, `HELPER`, `TTL`, `MAX`, `MIN`, or a leading separate `NO`, in every spelling; boolean-style flags never take the next word; `tokenizer` and `tokens` as a count are not secret-named (source: request)
- Token shapes: Stripe `sk_live_`/`rk_live_`/`sk_test_` + 24, GitLab `glpat-` + 20, npm `npm_` + 36, Google `AIza` + 35, Slack `xapp-`, three-part `eyJ` JWTs, replaced inside URLs, quoted strings and JSON string values (source: request)
- Real secret names (`API_TOKEN`, `--password`, `DB_PASSWORD`, `client-secret`) stay secret-named; everything redacted today stays redacted; bounding and logging are otherwise unchanged (source: request)

## Source comparison
- Problem, leaks in value forms (`"password":"…"`, `password: …`, `X-Api-Key: …`, `Cookie`, `-u admin:PASSWORD`, `$'…'`, `--secret=\"…\"`): rule 4. The reproductions pass on today's tree for the -H, pair, `-u` and quoting forms (delivered by k-arg-redact-quoting-and-keyvalue-forms) and are kept as regression rows. The Cookie value outside `-H` and a secret-named header value with spaces are the remaining gaps; see the first outline rows and rule 4.
- Problem, unrecognised names (`accessToken`, `clientSecret`, `privateKey`, `_authToken`, `refreshToken`, `AWS_CREDENTIALS`, `DOCKER_SECRETS`, `--cookie`, `ENCRYPTION_KEY`): rules 1–2. These are the first outline, the JSON-key scenario and the environment outline.
- Problem, missing token shapes (Stripe, GitLab, npm, Google, `xapp-`, JWT): rule 5. These are the token outline, the URL and JSON-value scenarios, and the near-miss scenario.
- Problem, masked harmless commands (`--max-tokens=4096`, `TOKEN_COUNT=5`, `--token-limit 5`, `PASSWORD_FILE=/path`, `--password-file /path`, `SECRET_NAME=prod`, `CREDENTIAL_HELPER=store`, `--password-stdin registry.example.com`, `--no-password db`): rule 3. These are kept by today's code (k-arg-redact-nonsecret-names) and stay as byte-for-byte rows, so the new plural and camelCase rules cannot bring them back.
- Need 1–4 and Synthetic acceptance cases 1–5: every listed literal appears in acceptance.feature with secret `s3cr3tVALUE9x`. Case 1's YAML `signingKey: s3cr3tVALUE9x` is a heredoc Bash call. `{"accessToken":"s3cr3tVALUE9x"}` appears both as a shell string and as a JSON tool input. Case 3 uses made-up values of the documented lengths. Case 5's environment clause is the environment outline.
- Conflict resolved: "plurals of its single words" makes `TOKENS` secret, while "`tokens` as a count" must not be. Rule 2 settles it by the value: a count keeps the name non-secret.
- Conflict resolved: "in every spelling" exemption versus "everything redacted today stays redacted". The request's explicit exemption wins (rule 3). The overlap is limited to camelCase spellings that end in an exempt word or start with `no`.
- Added from rule wording, not new scope: boundary rows for the minimum token lengths (rule 5), `db.password` as a JSON key (the `.` split), `API_TOKENS`/`tool --tokens 4096` (the count decision), and the run-together compounds and new pairs as assignment rows.
- Superseded Intents: k-arg-redact-quoting-and-keyvalue-forms, k-arg-redact-secret-name-forms, k-arg-redact-nonsecret-names, k-exec-token-pattern-coverage. Their committed acceptance files and the k-tool-args-log feature are not edited; their expectations agree with these rules.
