# Deny agent writes to an in-checkout artifact dir

Slug: k-exec-artifact-dir-inside-checkout
Model: not applicable — Start derives one boolean from two resolved paths and the pretool decision stays a stateless function of the policy and one path; no new state or interacting rules
Acceptance:
- .kogen/intents/k-exec-artifact-dir-inside-checkout/acceptance.feature
- features/steps/k-exec-artifact-dir-inside-checkout__steps.js

The Claude Code adapter (`executor/claudecode`) keeps its guard state in the executor artifact directory `Task.Dir`: the hook policy `hook-policy.json`, the hook log `hook-log.jsonl`, the hook settings `claude-settings.json` and the round files. Today `Start` (`executor/claudecode/claudecode.go`) never compares that directory with the checkout. The pretool hook's `decide` (`executor/claudecode/hook.go`) allows every in-checkout path that is not a protected path and not under `.git`. So when the directory lies inside the checkout, the agent's own Write/Edit/MultiEdit/NotebookEdit calls may rewrite the policy, which removes protection for later calls, or forge hook-log records. After this change, an artifact directory that is the checkout, inside it, or a parent of it is denied to those tools and recorded on the start event. An artifact directory outside the checkout behaves exactly as today.

Rules:
1. Detection at Start. Start resolves the checkout as today (`root`, via `filepath.EvalSymlinks(t.Root)`). After `os.MkdirAll(t.Dir)` and `filepath.Abs`, it also resolves the artifact directory through its symlinks with `filepath.EvalSymlinks`. A failure there makes Start fail with `executor.ReasonUnavailable`, like the existing artifact-directory errors. The artifact directory is *in the checkout* when its resolved path is the resolved checkout, below it, or an ancestor of it. Paths are compared by whole components, case-insensitively, with the hook's existing `within`. A sibling such as `$ABS/r2/exec` is not in the checkout for checkout `$ABS/r`. The rule applies to every role.
2. Policy. When the directory is in the checkout, the hook policy gains one field, `"artifact_dir": "<resolved artifact directory>"` (Go: `ArtifactDir string` with `json:"artifact_dir,omitempty"`). Otherwise the policy is byte-for-byte today's shape: the keys `root`, `protected`, `log`, `nonce` and, for Shape, `read_only`, with no `artifact_dir` key. All other policy fields are unchanged in both cases. In particular, `log` keeps today's spelling `filepath.Join(<Abs(t.Dir)>, "hook-log.jsonl")`, which is not resolved. `protected` is unchanged; the artifact directory is not added to it.
3. Start event. When the directory is in the checkout, `executor_started` carries `"artifact_dir_in_checkout": true`. Otherwise the key is absent. No other start-event field changes.
4. Pretool decision. When the policy has `artifact_dir`, `decide` refuses a target that lies within it (the directory itself or anything below it). The reason is exactly `this is the executor artifact directory (<artifact_dir>)`. The hook answer prefixes it with `Kogen: ` as for every denial, and the hook log record holds the unprefixed reason. Both spellings of the target that `decide` already computes, lexical and symlink-resolved, are compared with both `artifact_dir` and `resolveReal(artifact_dir)`. This is the same any-spelling matching protected paths use, so symlinks inside or outside the checkout and relative paths are all covered. Check order: read-only, then outside the checkout, then the artifact directory, then `.git`, then protected paths. So an outside path keeps the reason `the path is outside the checkout`, and a Shape call keeps the read-only reason. When the artifact directory is the checkout or one of its ancestors, every in-checkout write is therefore refused with the artifact-directory reason.
5. The hook log stays writable by the hook processes. `RunHook` appends its sentinel records directly (`appendSentinel`), not through `decide`, so pretool and posttool records keep being appended, including for the denied calls. The round's liveness check (`toolResults`, `checkUnanswered` in `executor/claudecode/stream.go`) is unchanged: a denied guarded call has its deny record, and a guarded call without a record still stops the round with `hook did not run for the <tool> call "<id>"; the round was stopped`.

Not changed: Bash remains observation only and is not prevented. The artifact directory's location is not refused, moved or redirected. `contract/` is not changed, because no existing pinned field, behavior or format changes and the additions are optional keys.

## Decisions
- An artifact directory that is the checkout, inside it, or a parent of it, after both are resolved through symlinks, is handled by one rule: the policy denies writes to it with a reason naming the artifact directory, and the start event records `artifact_dir_in_checkout: true`. (source: request)
- The denial covers every spelling of the path, including spellings through symlinks and relative paths, like protected paths. (source: request)
- An artifact directory outside the checkout changes nothing: the same policy and the same start event, without an `artifact_dir_in_checkout` key. (source: request)
- The hook log stays writable by the hook processes. (source: request)
- Technical choice: the denied path is a new optional policy field `artifact_dir` (the resolved directory), not an entry in `protected`. `protected` holds repository-relative entries, and an ancestor of the checkout has no repository-relative spelling. The field also lets the reason name the directory. Its exact reason text is `this is the executor artifact directory (<artifact_dir>)`. (source: request)
- Technical choice: when the artifact directory is the checkout or one of its ancestors, the single rule denies every in-checkout file-tool write with the artifact-directory reason. This is the direct consequence of "a parent of it is handled by one clear rule". (source: request)

## Tests
- Start records `artifact_dir_in_checkout: true` and writes `artifact_dir` (the resolved path) for an artifact directory inside the checkout, equal to it, an ancestor of it, or reaching it through a symlink outside it: new cases in a test file in `executor/claudecode` using the existing fake harness (`newHarness`), plus the acceptance scenarios (integration)
- An artifact directory outside the checkout, including a sibling `r2/exec`, leaves the policy keys and the start-event keys exactly as today: harness cases asserting the absent keys (integration)
- Pretool denies a target within `artifact_dir` by its lexical, relative, in-checkout-symlink and outside-symlink spellings, with the reason `this is the executor artifact directory (<dir>)`, while a sibling path stays allowed and the outside, read-only, `.git` and protected reasons keep their order: new `decide`/`RunHook` cases in `executor/claudecode/hook_test.go` (unit)
- In a round, a Write to the artifact directory is denied, its deny record is in the hook log, the round succeeds, and the policy file is unchanged, while pretool and posttool keep appending: a fake round in the harness, plus the round scenario (integration)
- The liveness check still stops a guarded call without a hook record: the existing `TestLivenessFailure`, plus the hookless-round scenario (existing)
