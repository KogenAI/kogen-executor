# Deny writes through hard links to protected files

Slug: k-exec-protected-hardlink-alias
Model: not applicable — Start records a fixed identity set once and the pretool decision stays a stateless function of the policy, the target's file metadata and the protected entries; no new state or interacting rules
Acceptance:
- .kogen/intents/k-exec-protected-hardlink-alias/acceptance.feature
- features/steps/k-exec-protected-hardlink-alias__steps.js

The Claude Code adapter's pretool hook (`RunHook pretool` → `decide` in `executor/claudecode/hook.go`) protects a path today by comparing the call's lexical and symlink-resolved path with the protected entries. A second name for the same file made with a hard link (same device and inode, no symlink) is a different path, so a Write/Edit/MultiEdit/NotebookEdit call to `alias.txt`, a hard link of the protected `locked.txt`, is allowed. The hook log records `allow`, and the protected file's content changes. After this change, the hook also compares file identity, and only for a call target that is an existing regular file with more than one link. When that identity equals the identity of a protected regular file, the call is denied and the reason names the protected entry. Every other decision is unchanged.

Rules:
1. Identity set at Start. When `Start` (`executor/claudecode/claudecode.go`) writes the hook policy, it also records the identity of every protected regular file that exists at that moment. Walk the policy's `protected` entries in order, as `filepath.Join(root, filepath.FromSlash(entry))`:
   - An entry that `os.Stat` reaches as a regular file (a symlinked entry is followed) gives one record.
   - An entry that is a directory: walk it with `filepath.WalkDir` (which does not follow symlinks inside it), starting at the directory's resolved path (`resolveReal`). Every regular file found gives one record that names the directory entry.
   - A missing entry, another file type, or an unreadable part of a walk is skipped. Identity collection never makes Start fail.
   The policy gains one optional field, `"protected_ids"`: an array of `{"entry":"<policy entry>","dev":<device>,"ino":<inode>}` in walk order, as unsigned integers taken from `syscall.Stat_t` (`uint64(st.Dev)`, `uint64(st.Ino)`). In Go this is `ProtectedIDs []fileID` with `json:"protected_ids,omitempty"`. The key is absent when no record exists. Every other policy field and the start event are unchanged. The package is Unix-only already (it uses `syscall.Kill`), so `syscall.Stat_t` is available.
2. Lazy check in the hook. In `decide`, after all existing checks (read-only, outside the checkout, artifact directory, `.git`, protected path), and only when they would allow: `os.Lstat` the resolved target. When that succeeds, the file is regular (`Mode().IsRegular()`) and its link count (`Stat_t.Nlink`) is above one, compare its (device, inode) with the following, and stop at the first match:
   a. the policy's `protected_ids`, in order;
   b. then the current identity of each policy `protected` entry that `os.Stat` now reaches as a regular file, in order. This re-check stats only the entries themselves. It does not walk protected directories.
   A match denies with exactly `this is a hard link to a protected path (<entry>)`, where `<entry>` is the matching record's or entry's policy spelling. When the target is missing, is not a regular file, or has a link count of one, no identity work is done: nothing is stat'ed besides the target, and nothing else is scanned. The decision is the existing allow, even when the target's identity is in `protected_ids` (for example a file that was moved out of a protected directory after Start and has one link).
3. Recording. The deny goes through `RunHook` like every other deny. The hook log gets a pretool sentinel with `decision: "deny"`, the resolved `path` and the unprefixed reason, before the hook answers. The hook answer's `permissionDecisionReason` is `Kogen: ` plus the reason. Allowed calls produce exactly today's records and no stdout.
4. Order and precedence. The existing checks run first, so their reasons win. A call to a protected file's own name, or through a symlink that resolves to it, keeps `this is a protected path (<entry>)` whatever its link count. A path that resolves outside the checkout (including a checkout symlink to a hard link outside it) keeps `the path is outside the checkout`. A read-only (Shape) role keeps its read-only reason.
5. Policies without `protected_ids` (older policy files, or the hand-written ones in `contract/` and the package tests) still deny a hard link to a protected file entry through rule 2b.

Not changed: an unprotected file with several links whose identity is not protected (for example two unprotected files hard-linked to each other) is allowed. A byte-identical copy (a different inode) is allowed. A file created inside a protected directory after Start is not in the identity set, and the hook does not walk directories, so a hard link to it from outside the directory is allowed. Bash stays observation only. `contract/` is not changed: `protected_ids` is an optional additive key, and the pinned hook behaviors are unchanged. This supersedes the statement in the earlier Intent `k-exec-artifact-dir-inside-checkout` that the policy written for an artifact directory outside the checkout keeps exactly the keys `root`, `protected`, `log`, `nonce` (and `read_only`): when a protected regular file exists, the policy now also has `protected_ids`.

Interfaces the acceptance capture relies on, which must keep their names and shapes: `RunHook(args, stdin, stdout, stderr) int`, the `policy` struct with its `Log`/`Nonce` fields, the `sentinel` struct (`Nonce`, `Hook`, `ToolUseID`, `ToolName`, `Path`, `Decision`, `Reason`), `newHarness`, `fakeConfig` and `fakeEnv.options` in the package tests. Do not add a test named `TestProtectedHardlinkAliasCapture` or a file `executor/claudecode/protected_hardlink_alias_capture_test.go`: the acceptance step generates them in a scratch copy.

## Decisions
- A write to an existing regular file with more than one link whose (device, inode) equals a protected regular file's is denied, and the reason names the protected entry: `this is a hard link to a protected path (<entry>)`. (source: request)
- A file inside a protected directory is recorded at Start under the directory's entry, so a hard link to it from outside the directory is denied with the directory's entry in the reason (`guarded`). The hook itself never scans a directory, so a file created in a protected directory after Start and hard-linked from outside it is allowed. (source: request)
- The identity set is computed when Start writes the policy. The hook re-checks lazily, and only for targets with a link count above one. Ordinary writes (link count one) do no identity comparison, stat or scan, so a target with one link is allowed even when its identity is in the Start set. The same file is denied once it gains a second link. (source: request)
- The deny is recorded in the hook log like any other deny; allowed calls are unchanged. (source: request)
- Technical choice: the reason text is new and distinct (`this is a hard link to a protected path (<entry>)`), so the log says why a path that is not itself protected was denied. Existing checks run first, so a protected name keeps `this is a protected path (<entry>)`. (source: request)
- Technical choice: the hook's lazy re-check (rule 2b) also stats the protected file entries themselves at call time. This keeps policies without `protected_ids` effective and covers a protected file created after Start, without scanning directories. (source: request)
- Technical choice: the test seam for platforms that refuse hard links is a test-only helper, `hardLinkOrSkip(t, oldname, newname)`, which calls `os.Link` and calls `t.Skipf` with the error when it fails. Only the hard-link tests use it, so every other hook test runs unchanged. No production seam is added. (source: request)

## Source comparison
- Problem (hard-link names pass the lexical/symlink comparison and the log records `allow`): addressed by rules 1–3. The baseline reproduction was observed: on the unchanged tree, `alias.txt`, `late.txt`, `loose.txt` and `moved-link.txt` are allowed.
- Need 1 (an existing regular target with more than one link; compare with every protected regular file that exists; deny naming the entry): rules 1, 2 and 4. Acceptance scenarios 1, 2 and 5.
- Need 2 (protected directory; no extra scan in the hook; links made from outside it to files that exist when the policy is written are covered): rule 1 (directory walk at Start) and rule 2 (no walk in the hook). Scenario 3 includes a link made after Start (`late.txt`) to a file that existed at Start. Scenario 4 shows that the hook does not walk the directory: `fresh-link.txt`, a link to a file created in `guarded` after Start, is allowed.
- Need 3 (computed at Start, re-checked lazily only for link count above one, so ordinary writes pay no scan): rules 1 and 2. Scenario 4 moves the recorded `guarded/inner.txt` out of the directory to `moved.txt` after Start. A write with one link is allowed, although its identity is in the Start set. After `moved-link.txt` is linked to it, the same file is denied under both names. This tells the link-count guard and the Start set apart from a hook that compares every target's identity, and from a hook that scans directories.
- Need 4 (deny names the entry and is in the hook log; allowed calls unchanged): rule 3. Every scenario checks the hook log records with the run nonce.
- Synthetic 1 (`locked.txt` protected, `alias.txt` via `os.Link("locked.txt", "alias.txt")`: denied, reason names `locked.txt`, content unchanged): scenario 1, by relative and absolute spelling, with `locked.txt` content `locked\n` unchanged.
- Synthetic 2 (`plain.txt`, no link, unprotected: allowed): scenario 1.
- Synthetic 3 (`copy.txt`, a byte-identical copy: allowed): scenario 1. The added counterexample `pair-a.txt`/`pair-b.txt` (an unprotected linked pair) is allowed too, which rules out "deny every link count above one".
- Synthetic 4 (protected file with one link, write to its own name: denied as before): scenario 2, first write (`links` 1, the existing reason). The same scenario also shows a link made after Start (`later.txt`) is denied, and that a protected entry that does not exist (`not-yet.txt`) is skipped.
- Synthetic 5 (a hard link outside the checkout to a protected file, a write through a checkout symlink: denied): scenario 5. `via-locked.txt -> locked.txt` (resolved path and identity both match; the path reason wins). `via-alias.txt -> alias.txt` (resolved to a hard link; the identity reason). `via-far.txt -> $ABS/outside/far.txt` and the outside link itself are denied as outside the checkout.
- Synthetic 6 (platform refuses hard links: test skipped, no other hook behavior changes): the `hardLinkOrSkip` test helper in the Go tests. The acceptance capture runs on this platform, where `os.Link` works. If `os.Link` is refused there, it fails with `os.Link(<old>, <new>) was refused, so the hard-link fixture cannot be built` rather than passing.
- Superseded: the earlier Intent `k-exec-artifact-dir-inside-checkout`'s exact policy key list, as described above.
- Omitted: nothing in the request.
