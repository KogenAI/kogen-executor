# Verify the Claude Code runtime before every use

Slug: kogen-runs-unverified-claude-code-runtime
Model: not applicable — the change is a stateless filesystem and ownership predicate plus a one-slot version answer tied to the executable's identity; there is no interacting session state to model
Acceptance:
- .kogen/intents/kogen-runs-unverified-claude-code-runtime/acceptance.feature
- features/steps/kogen-runs-unverified-claude-code-runtime__steps.js

Kogen promises to run only its pinned, tested Claude Code from its own managed folder and hands that program the stored sign-in token. Before the managed runtime is used for anything (the version probe behind `Describe` and `Start`, the sign-in check, every role start, `Probe`, `SetupToken`) the adapter accepts it only when all of these hold:

1. The runtime path resolves (links followed) to a regular, executable, non-empty file. Install and use share this one definition of "present".
2. Its size equals the pinned size of the platform (a stat, no hashing). The expected size is unknown, and the check skipped, exactly when the test origin variable `KOGEN_CLAUDE_CODE_URL` is set.
3. The resolved file, the version folder (`RuntimeDir`) and the managed root (`Root`) are owned by the current user and are not writable by group or others. A runtime only its owner can write, including mode 0555, is accepted.
4. The version answer describes the file in use now. A version answer is remembered only together with the identity of the file that gave it (same file, same size, same modification time). A replaced executable, by rename or by rewriting in place, is asked for its version again; an unchanged supported runtime is reused with nothing more than the stat checks above, with no further `--version` run.

A violation fails as `executor/unavailable` before any child process starts and before the stored token is read. The message names the offending path and the specific problem: dangling link, directory, not executable, empty, the actual and the expected size, another owner, writable by group, writable by others, or the unsupported version. It tells the user to remove the version folder and run again. The adapter never deletes, rewrites or chmods the runtime, its folder or a link or target. A completely absent runtime is still installed as today. `Describe` on a runtime refused by the checks above returns the descriptor with version `claude-code unknown` and does not fail. No message contains the stored token.

This replaces the narrower earlier intents k-exec-runtime-version-cache, k-exec-runtime-entry-unusable, k-exec-runtime-size-matches-pin and k-exec-runtime-not-writable-by-others. Existing tests that put a small stand-in at the runtime path with the default pin now meet the size check; they must declare the size unknown (set `KOGEN_CLAUDE_CODE_URL`; no download happens while the file is present) or use a stand-in of the pinned size.

## Decisions
- "Present" is one definition, the resolved regular, executable, non-empty file, shared by ensureRuntime, the install-lock recheck and binary; existing kind wording and the 'remove <RuntimeDir> and run again' remedy are kept; an absent entry still installs. (decision: D1, round 1) (constraint: keep the kind phrases 'dangling', 'directory', 'empty', 'not executable' and the remove-and-run-again remedy) (constraint: absent runtime still installs) (evidence: executor/claudecode/runtime.go; executor/claudecode/runtime_test.go; executor/claudecode/claudecode.go) (source: request)
- The pinned size is the expected size unless KOGEN_CLAUDE_CODE_URL is set; then the expected size is unknown and only the size check is skipped. (decision: D2, round 1) (constraint: existing stand-in tests in executor/claudecode and contract must set the variable or use a pinned-size stand-in) (constraint: owner and permission checks still apply under the test origin) (evidence: executor/claudecode/runtime.go; executor/claudecode/fake_test.go; contract/fake_claude_test.go; executor/claudecode/setup_token_test.go) (assumption: A scratch prototype of this rule showed about 55 existing claudecode tests failing on the size check until their stand-ins declare an unknown size; the request does not name a different signal for unknown size.) (source: request)
- Owner and write-permission checks apply to the resolved runtime file, the version folder and the managed root: owner is the effective user, group and other write bits clear; mode 0555 accepted; existing root tightening to 0700 in ensureRuntime is unchanged and nothing else is chmodded. (decision: D3, round 1) (constraint: the adapter never deletes, rewrites or chmods the runtime or its folder) (evidence: executor/claudecode/runtime.go) (source: request)
- The checks run inside binary, so Describe (version unknown), Start, Probe and SetupToken refuse before any child process or token read. (decision: D4, round 1) (evidence: executor/claudecode/claudecode.go; executor/claudecode/setup_token.go) (source: request)
- The version answer is remembered only with the identity (same file, size, modification time) of the file that gave it; an unchanged file is not asked again; unsupported-version refusal wording and Describe's honest answer for a replacement stay as in the baseline. (decision: D5, round 1) (evidence: executor/claudecode/claudecode.go; executor/claudecode/version_observation_test.go; executor/claudecode/adapter_test.go) (assumption: File identity plus size plus modification time is not proof against a rewrite that preserves all three; the acceptance waits 100 ms before replacing so coarse timestamp granularity cannot hide the replacement.) (source: request)
- The acceptance makes a runtime absent by removing the whole version folder; an empty version folder left behind is outside this request. (decision: D6, round 1) (evidence: executor/claudecode/runtime.go) (assumption: Observed only in a scratch prototype run outside the repository, not via a retained probe.) (source: request)
- The acceptance drives the real adapter through a Go driver the step file builds from the public API; stand-ins are sparse-padded shell scripts that log every invocation; foreign ownership is covered by a unit test of the owner and mode predicate, not by acceptance. (decision: D7, round 1) (evidence: executor/claudecode/runtime.go; .kogen/intents/k-exec-runtime-entry-unusable/intent.md) (source: request)

## Source comparison
- Addressed: Problem 1 (version answer outliving the executable): rename and rewrite replacement scenarios "A replaced runtime is checked again by the same adapter"; the unchanged-reuse scenario "An unchanged supported runtime is not asked for its version again" requires exactly one `--version` run across `Describe` and two `Start`s. Baseline: `claudeVersion` already probes on every call (claudecode.go, version_observation_test.go), so refusal of a replacement is preserved and only the reuse is new.
- Addressed: Problem 2 (dangling link, directory, empty, non-executable never repaired): scenario outline "An unusable runtime entry is refused, left alone and installed after its folder is removed" with the folder named, nothing deleted, `Describe` unknown, no invocation, and one download after the user removes the folder. Baseline: runtimeUsable in runtime.go already refuses these; the scenarios preserve that wording.
- Addressed: Problem 3 (truncated or extended file): scenarios "A runtime one byte short of the pinned size is refused" and "A runtime one byte over the pinned size is refused" name the path, both sizes and the remove-and-rerun instruction and leave the file untouched.
- Addressed: Problem 4 (owner and permissions): scenarios for runtime 0775, runtime 0757, version folder 0777, plus "A group-writable managed root hides the version" (managed root 0775 observed through `Describe`, which runs no `ensureRuntime`); accepted cases are the 0755 runtime, the 0555 runtime and a symlinked runtime whose target passes. Foreign owner: unit test, not acceptance.
- Addressed: Synthetic acceptance 5 missing replacement: scenario "A removed runtime is reported absent and installed again" (Describe unknown, then one download and a successful Start from the test origin). Synthetic acceptance 6: every refusal scenario ends with "no message contains the stored token".
- Addressed: delivery notes: each scenario's When step runs the real adapter in a scratch home built from literals and records every answer, the invocation log, the download count, the version folder snapshot and the driver's exit status and output; the Then steps assert on that record only. Nothing the Build adds is read in a Given or When; the preserved behaviours are quoted above from runtime.go and claudecode.go.
- Superseded: the four earlier intents named above; their stand-in fixtures with small files are not valid under the size rule.

## Tests
- Present means a resolved regular, executable, non-empty file, shared by ensure, install recheck and binary: extend TestUnusableRuntimeEntries in executor/claudecode/runtime_test.go (regression)
- Pinned-size rule: a table test with the pinned size accepted, one byte less and one byte more refused with both sizes named, and the size unknown when KOGEN_CLAUDE_CODE_URL is set (unit)
- Owner and write permission rule over the file, version folder and managed root: a test of the owner and mode predicate with 0755 and 0555 accepted, 0775, 0757 and 0777 refused, and a foreign owner id refused (unit)
- Version answer bound to the executable: extend executor/claudecode/version_observation_test.go with an unchanged-reuse run count and rename and rewrite re-probes (regression)
- Refusals precede any child and token read, name path and problem, leave the folder unchanged and never contain the token: the acceptance scenarios (scenario)
- Stand-ins in existing suites meet the size rule: update executor/claudecode/fake_test.go, setup_token_test.go, version_observation_test.go and contract/fake_claude_test.go so their stand-ins declare the size unknown (existing)
